### 1. Состояние «Папки с документами»: one-shot vs «держится проектом»
- **Что ждёт:** финальное решение о поведении вооружения код-сводки материалов.
- **Почему без него/вестака:** продуктовый выбор поведения, есть развилка.
- **Сделано вокруг:** реализован и запушен **one-shot** (вооружение на одну
  следующую отправку, снимается на отправке/смене чата/смене проекта). Причина
  отхода от «держится проектом»: при персисте «не открывал N» кричало бы на
  каждом follow-up, где модель не перечитала все документы, — тот шум, ради
  устранения которого сводка молчит на «прочитано N из N». Флаг отправлен вестаку.
- **Решение одной строкой:** оставить one-shot ИЛИ переиграть на персистентный
  per-project флаг (осознанный шум на follow-up; меняется одним местом в
  `send-chat-message.ts` + хранение per-project).

## 02.08 — инструменты браузера работают БЕЗ открытой вкладки (PersistentBrowser)

Павел на живой задаче: «можешь открыть сайт альфы и посмотреть какие там у нас
офферы». `browser_navigate` вернул «вкладка Browser не открыта», агент минуту читал
локальные файлы, ЗАЦИКЛИЛСЯ (анти-повтор заблокировал третий одинаковый `read_file`)
и закончил тем, что попросил ПАВЛА открыть вкладку и написать «открыл». Его вердикт:
«не работает». Он прав.

**Причина:** `window.verstakBrowser` ставится в useEffect при монтировании
`BrowserView`, а App монтировал его ТОЛЬКО на своей вкладке
(`{activeView === 'browser' && <BrowserView/>}`). Пока вкладку ни разу не открыли —
API нет, `browser.ts` отдаёт «вкладка не открыта». Дали агенту зрение/клик/ввод/
ожидание и оставили условие, при котором всё это недоступно, пока человек сам не
нажмёт вкладку. Требование №5 ТЗ (вкладка — окно НАБЛЮДЕНИЯ, не условие работы) и №2
(один браузер) нарушались.

**Путь A (дешёвый, выбран — честно проверен, не по надежде):** держать `BrowserView`
смонтированным всегда, скрывать `display:none`, когда вкладка не выбрана
(`src/components/PersistentBrowser.tsx`; App рендерит его БЕЗУСЛОВНО). Опасение
постановщика — «скрытый webview может спать и не исполнять executeJavaScript» —
снято ТРЕМЯ живыми смоук-прогонами на Electron 40 (scratchpad, не в репо):
(1) `display:none` webview исполняет `executeJavaScript` и `loadURL`; (2) скрытый
С РОЖДЕНИЯ (вкладку не открывали ни разу) — `did-attach-webview` срабатывает, тот же
результат; (3) агент навигировал скрытый webview → человек открыл вкладку → видит
РОВНО страницу агента, не перезагрузку. Путь B (webContents в main) не понадобился.

**SEC-CMD не тронут:** гейты (`plan` не кликает, правила судят URL/селектор, попап
под теми же проверками) живут в `browserHandler` (electron), ДО `window.verstakBrowser`.
Правка чисто рендерная (монтирование), путь исполнения инструмента не менялся —
security-пины (`browser-plan-mode`, `browser-url-rules`, `popup-navigation`) зелёные
ПОТОМУ, что новый путь проходит тот же `browserHandler`.

**Пин (jsdom, `persistent-browser-mount.test.ts`, +3):** при невыбранной вкладке
(`active=false`, случай «первый запуск, вкладку не открывали») `window.verstakBrowser`
ВСЁ РАВНО есть и умеет navigate/snapshot; слот скрыт `display:none` вне своей вкладки
и `display:contents` на ней; размонтирование снимает API. Мутация (вернуть
`{active && <BrowserView/>}`) роняет главный пин — не декоративен. Эталон 4571→4574.

**В ЖУРНАЛ (мелкое, НЕ чинил — по указанию постановщика):** при отказе браузера
агент заметался — три одинаковых `read_file` подряд, спасла анти-повтор-защита. Это
признак, что на отказ инструмента агент мечется вместо того, чтобы сразу сказать «не
могу». Кандидат на отдельную правку (ранний честный отказ вместо цикла).

**Версия:** тянет на 2.4.1 отдельным релизом (у Павла болит сегодня) — решение
постановщика после приёмки.

## 02.08 — стартовая ГОНКА браузера («иногда работает») закрыта ожиданием готовности

Живая проверка a0f7a22 у Павла: `browser_navigate` в ОДНОМ прогоне вернул старую
ошибку «вкладка Browser не открыта», в следующем ТОТ ЖЕ вызов отработал — между
попытками ничего не менялось. «Иногда работает» хуже, чем «не работает»: второе
чинят, первое списывают на случайность.

**Факт установлен по коду, не по догадке.** Обе попытки шли на ОДНОМ коде (a0f7a22,
`PersistentBrowser` уже смонтирован-всегда) — значит не старая сборка. `PersistentBrowser`
монтируется в renderer АСИНХРОННО (lazy-chunk), а `browser.ts` при отсутствии
`window.verstakBrowser` отдавал ошибку НЕМЕДЛЕННО (единственный `exec`, `if (!api)
return __err` — проверено). Если прогон дошёл до браузерного инструмента раньше, чем
закончилось монтирование, API ещё нет → «не открыта»; следующий вызов (уже
смонтирован) проходит. Разница только во времени → **гонка старта**, не третья
причина.

**Лечение — честное ожидание готовности (не слепая пауза), `browser-ready.ts`:**
сниппет теперь возвращает `{ __vskNotReady:true }`, когда API нет (в странице
действие при этом НЕ выполняется — повтор безопасен и для мутаций);
`execAwaitingBrowserApi` повторяет вызов с шагом 50мс до предела (3с), выполняет,
как только API появился, и отдаёт честную ошибку «повтори попытку», только если не
появился за лимит. SEC-CMD не затронут: гейты в `handle()` ДО `dispatchBrowser`,
ожидание — после них. **Пин (`tests/ipc/browser-ready.test.ts`, +3):** вызов раньше
монтирования (API нет → появился) → дождался и выполнил; готов сразу → один вызов;
не появился никогда → `__vskNotReady` после предела, цикл ограничен. Мутация (убрать
цикл) роняет пин про гонку — не декоративен. Эталон 4574→4577.

**В ЖУРНАЛ (НЕ чинил сейчас, по указанию постановщика):**
1. **Внутренний монолог модели на английском вылезает НАРУЖУ.** В ответе агента
   пользователю (русский продукт, русский запрос) появились «I'm hitting a wall with
   this browser tab», «Let me test it again», «I need to locate the specific
   sections». Человек это видит, выглядит сыростью. Кандидат на правку (язык ответа
   = язык пользователя; внутренние размышления не в user-facing поток).
2. **Лимит шагов режет реальную задачу.** Работа оборвалась по лимиту шагов на
   середине правки лендинга — часть плейсхолдеров заполнена, часть нет. Агент честно
   перечислил остаток (это правильно), но человек получил наполовину сделанный файл.
   Кандидат: поднять/адаптировать лимит под объём реальной задачи или продолжать
   после явного согласия, а не обрывать.

**2.4.1 ПРИДЕРЖАНА** до приёмки этой починки — «иногда работает» выпускать нельзя
(решение вестака).
