## Шаг 1 (модуль 1). Кэш промпта по провайдерам

Метод: три коротких хода одного чата; system собирается на каждом ходе тем же
путём, что продовый `ai:send` (`prepareSystemContext` → `systemForProvider`),
инструменты — как `runner-api.ts:954-978` (79 тулзов); доля кэша =
`cached_tokens / prompt_tokens` из usage провайдера. Ключи расшифровываются
только в дочернем Electron-процессе (safeStorage/DPAPI), значения никуда не
пишутся. Упрощения бенча: `memories=[]`, `brainContext=null` (оба блока живут в
volatile-хвосте ПОСЛЕ кэш-маркера — на стабильный префикс не влияют).

Запуск:

```
node scripts/bench/prompt-cache-bench.mjs --project <путь> [--freeze-system] [--dry]
```

| провайдер | модель | ход 2 кэш | ход 3 кэш | виновник низкого числа |
|---|---|---|---|---|
| deepseek | deepseek-v4-flash | **6%** (1408/23022) | **99%** (22912/23052) | пересборка volatile-хвоста system между ходами — см. разбор ниже |
| verstak-gateway | kimi-k2.7-code | нет данных (поле отсутствует) | **99%** (24064/24323) | релей/апстрим не вернул `prompt_tokens_details` на ходах 1–2 — вне этого репозитория (сервер agi-iri) |
| kimi-coding | kimi-for-coding | — | — | 402 «unable to verify membership» — подписка Kimi не активна, замер недоступен |
| zai-coding | glm-5.2 | — | — | 429 «Insufficient balance» — баланс Z.ai пуст, замер недоступен |
| custom-openai | claude-opus-4-8 | нет данных | нет данных | endpoint не отдаёт `prompt_tokens_details` вовсе, а `prompt_tokens` мусорный (2 / 2 / 30523) — замер невозможен |
| остальные 9 | — | — | — | ключей нет (булев чек settings) |

### Разбор deepseek (единственный полный замер)

**Ход 2 низкий (6%) — виновник назван и доказан контрольным кейсом.**
Диагностика бенча дифает system-строки соседних ходов байтово:

- стабильный префикс до `CACHE_BREAKPOINT` (10 533 символа) **байт-в-байт
  идентичен** на всех трёх ходах — сборка промпта под кэш работает;
- расхождение ход1→ход2 — в volatile-хвосте: строка `first_turn: true…`
  ([context-pack.ts:162](../electron/ai/context-pack.ts)) есть только на ходе 1.
  В проде к ней добавляются: recall памяти — блок «Память агента» инжектится
  только в первый send чата ([memory-context.ts:82-88](../electron/ipc/ai-send/memory-context.ts)),
  карта проекта/граф, появляющиеся в кэше между ходами
  ([context-pack.ts:228-238](../electron/ai/context-pack.ts)), и git-status,
  меняющийся после каждой записи файла ([context-pack.ts:192](../electron/ai/context-pack.ts));
- поскольку у OpenAI-совместимых провайдеров весь system (вместе с хвостом) —
  это `messages[0]`, один изменённый байт хвоста инвалидирует префикс-кэш для
  ВСЕЙ истории и инструментов, идущих после: на ходе 2 кэш взял только
  стабильную часть system (~1.4k токенов), а ~21.5k токенов (tools + остальное)
  ушли мимо кэша.

**Контрольный кейс** (`--freeze-system`, §3.1 «у „не произошло“ должен быть
кейс, где происходит»): та же цепочка с system, собранной один раз, — ход 2
даёт **99%** (22912/23182). Значит виновник именно пересборка хвоста, а не
латентность кэша DeepSeek. Бонус-факт: кэш DeepSeek пережил перезапуск процесса
и минуты паузы (ход 1 контрольного прогона сразу 99% от предыдущего запуска).

### Выводы модуля 1

1. **Сборка промпта под кэш работает, переписывать нечего** (подтверждает
   постановку). На стабилизировавшемся чате (ход 3+) кэш бьёт на 99% у обоих
   измеримых провайдеров.
2. Систематический мисс один — ход 1→2, из-за одноразовых блоков хвоста
   (first_turn, recall памяти). Цена: ~20k токенов кэш-миса один раз на чат —
   у DeepSeek это копейки. Возможная стройка (НЕ делалась — вне постановки):
   переезд volatile-хвоста из system-сообщения в конец диалога, чтобы история и
   tools кэшировались независимо от хвоста, — отдельное решение со своими
   рисками (семантика промпта).
3. `custom-openai` endpoint (`claude-opus-4-8`) не возвращает пригодный usage →
   **cost-контроллер Verstak на этом провайдере считает мимо** (input 2 токена
   на ходах со стримом). Побочная находка, требует отдельной задачи. Плюс: на
   OpenAI-совместимом пути Anthropic-модель не получает explicit `cache_control`
   (маркер снимается `systemForProvider` — так и задумано для этого транспорта),
   т.е. кэш там зависит целиком от релея.
4. kimi-coding / zai-coding — повторить замер после оживления подписки/баланса
   (одна команда, см. выше).

## Шаг 2 (модуль 4). Что держит main-поток

Метод: каждая операция-кандидат ТЗ исполняется реальным модулем, меряются стена
и **максимальный одиночный стоп event-loop** (`perf_hooks.monitorEventLoopDelay`,
разрешение 5 мс) — это и есть «блокирует ли UI» числом: у синхронного вызова
стоп ≈ длительности, у по-настоящему асинхронного (ripgrep — child process,
контрольный кейс) — близок к нулю. SQLite меряется на **online-backup-копии
живой БД** (8 МБ), оригинал не трогается. Большой каталог — `Downloads`,
**45 200 файлов** (тот же класс, что в инцидентах Д1).

Запуск:

```
node scripts/bench/main-thread-bench.mjs --project <большой каталог> [--skip-heavy | --only-heavy]
```

Оговорка о воспроизводимости: wall-времена операций, гуляющих по диску
(find_files, list_directory, search_project), между прогонами отличаются в
5–25 раз (дисковый кэш ОС / антивирус) — поэтому даны диапазонами; их **stall**
при этом стабильно остаётся в сотнях миллисекунд максимум.

### Выводы модуля 4

1. **Секундных блокировок main-потока нет ни у одного кандидата ТЗ.**
   Максимальный одиночный стоп из всех замеров — ~0.17 с (maskSecretsForDiff на
   640KB), у графа зависимостей при 86.8 с стены — стопы ≤0.15 с (он читает и
   парсит мелкими кусками). Редкие всплески 0.3–0.6 с при обходе дерева
   нестабильны между прогонами (похоже на дисковую конкуренцию, не на наш CPU).
2. **SQLite выносить в worker не за чем** — весь синхронный better-sqlite3 стоит
   единицы миллисекунд на операцию (~8 мс/ход событиями + ~5 мс чекпойнт).
   `safeRealJoin` подозрение постановки подтверждено — дешёвая функция.
3. **Единственный содержательный кандидат на worker_threads — secret-scanner на
   больших блобах**: путь подтверждения записи большого файла = scanText(before)
   + maskSecretsForDiff ≈ 0.2 с синхронно; scanText зовётся на каждом крупном
   tool-result (~40 мс/МБ). Но и это стопы <0.2 с — решение «строить ли шаг 3
   вообще» теперь принимается по этим числам, а не по списку подозреваемых.
4. Реальная цена большого каталога — **wall-латентность самих инструментов**
   (find_files 27–145 с: модель ждёт результат минуты), но это не блокировка
   UI (stall ≤0.6 с) и не worker-вопрос — это отдельный класс работ про
   алгоритмы обхода/кэши, если решим брать.
