# Задача 7 — Workflows и Решения: предложение (сценарий + конкуренты)

Оба раздела сейчас `soon` (выключены в меню) — «нужен понятный сценарий создания,
запуска и статусов». Разбор через /pavel-ux-ui (сценарий/вид) + /pavel-bos-mkt
(конкуренты). Предложение до кода.

## Что это сейчас (факт по коду)
- **Workflows** = `WorkflowsPanel` (каталог-лаунчер готовых Agency Workflows: карточка
  id/name/desc/N шагов + бриф + «Запустить» → инжект промпта в чат) + `WorkflowView`
  (read-only история пайплайнов). Субстрат уже есть: мультиагент delegate/parallel/
  orchestrate/swarm (`multi-agent-templates`: Оркестратор/Рой/Параллельно). Чего нет —
  понятного пути «собрать свой процесс → запустить → видеть статусы шагов».
- **Решения** = `DecisionsPanel` («Решения проекта») — список decision-record'ов
  (что решили + почему + уверенность), из Project Brain. Чего нет — сценария: КОГДА
  решение заводится, КАК влияет на будущие прогоны, зачем пользователю сюда ходить.

## Конкуренты (позиционирование)
| Продукт | Workflows | Решения/память решений |
|---|---|---|
| Cursor / Antigravity | Нет явных user-workflow; всё в чате. Rules-файлы. | Нет отдельной сущности «решение». |
| Claude Code | Skills/slash + хуки; workflow = скилл. | Нет. |
| Open Design (наш разбор №9) | **Automation**: ingest источник → PROPOSAL (create/apply/reject) → расписание (`routes/automation*`). Пайплайны в манифесте плагина (stages/atoms/onFailure). | Нет отдельного, но есть handoff-синтез диалога. |
| n8n / Dify | Визуальный билдер узлов — мощно, но тяжело и «не про кодинг-агента». | — |

**Вывод рынка:** никто из КОДИНГ-агентов не сделал «workflow как продукт» понятным.
Ниша Verstak (контроль/прозрачность) → workflow не как визуальный граф узлов (n8n —
чужая поляна), а как **сохранённый, повторяемый, наблюдаемый прогон агента**. Это
прямое продолжение того, что уже есть (multi-agent + planздесь + agent_runs).

## Предложение

### Workflows — «повторяемый прогон», а не граф узлов
Сценарий из трёх глаголов, без билдера:
1. **СОХРАНИТЬ.** У успешного прогона в «Истории работы» (задача 1) — кнопка
   «Сохранить как workflow» (переиспользует уже существующий Skill-Capture из RunDetail).
   Workflow = имя + бриф-шаблон + шаги (из плана прогона) + дефолтные агенты/модели.
2. **ЗАПУСТИТЬ.** Каталог (нынешний WorkflowsPanel) — карточка → поле брифа → «Запустить».
   Уже работает; довести UX и снять `soon`.
3. **СТАТУСЫ.** Запущенный workflow — это обычный agent_run → его статусы шагов уже
   рисует конвейер в «Истории работы»/Обзор. Не строим второй трекер: workflow-прогон
   открывается там же. Отдельная вкладка «Автозапуски» — только для запусков по расписанию
   (пересечение с задачей 8/9-automation).
Так «создание/запуск/статусы» закрываются переиспользованием готового (Skill-Capture +
каталог + конвейер прогона), а не новой подсистемой. Снять `soon` можно после п.1+п.3.

### Решения — «почему так сделано», привязанные к прогону
Проблема: decision-record'ы висят списком без причины заходить. Сценарий:
1. **ЗАВОДЯТСЯ по ходу.** Агент фиксирует решение (что выбрал + почему + уверенность)
   как сейчас, НО с привязкой к runId/сообщению.
2. **ВИДНЫ в контексте.** Решение показывается у прогона (вкладка Обзор/Диагностика) и
   всплывает, когда агент собирается сделать иначе («ранее решили X — точно меняем?»).
3. **Раздел «Решения» = журнал ПОЧЕМУ**, с фильтром по файлу/прогону. Ценность —
   «почему тут так», а не абстрактный список.
Это делает Решения продолжением прозрачности (edge Verstak), а не мёртвой вкладкой.
Снять `soon` после привязки к runId + показа в контексте.

## Что не делаем
- НЕ визуальный node-билдер (n8n/Dify) — чужая ниша, тяжело, против «контроля через
  прозрачный прогон».
- НЕ второй трекер статусов — статусы шага живут в конвейере прогона (задача 1).

Рекомендация: **Workflow = сохранённый повторяемый прогон** (три глагола, всё
переиспользуется), **Решения = журнал ПОЧЕМУ, привязанный к прогону**. Оба снимают `soon`
малыми шагами поверх уже построенного. Финальный вид/приоритет — решение Павла (это его
продуктовое видение). Код — после «да».
