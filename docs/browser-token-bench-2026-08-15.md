# Токен-бенчмарк страниц встроенного браузера и фиксация порогов (P3, кусок 2)

Дата: 2026-08-15. База: `9635274`, версия 2.6.3. Electron 40.10.0 / Chrome 144.0.7559.236.
Постановка: `детали/browser-p3.md`, кусок 2.

**Воспроизведение:**

```bash
npm run bench:browser-page -- --repeats 3 --project <путь-к-проекту> --json report.json
```

```bash
npm run bench:browser-run -- --project <путь-к-проекту> --providers deepseek,verstak-gateway --json runs.json
```

Оба измерителя гоняют ПРОДОВЫЙ код: `shared/browser-snapshot.ts` инжектится в страницу
через `.toString()` — тем же приёмом, что `BrowserView.tsx`. Полезная нагрузка считается
как в проде: объект из `tool-handlers/browser.ts`, сериализованный `JSON.stringify`
(`runner-api.ts:1556`), оценка токенов — формула `estimateTokens` (`context-limits.ts`).

---

## 1. Что зафиксировано

**Порог `VSK_SNAPSHOT_TOP_N`: 150 → 50.** Обоснование и цена решения записаны рядом с
самой константой в `shared/browser-snapshot.ts`, а не только здесь.

**Правило выбора инструмента (по медианам замера):**

| нужно | инструмент | цена, токенов |
|---|---|---|
| адресоваться к элементу | `browser_find` | 56–444 (медиана 89) |
| карта страницы | `browser_snapshot` (top-50) | 44–989 |
| содержимое страницы | `browser_read_page` **с селектором** | без селектора до 4 466 |

Порядок именно такой: `find` не зависит от размера страницы, снимок зависит линейно
(14.4–17.8 токена на элемент), а `read_page` без селектора на тяжёлой странице дороже
их обоих.

### Ранги целей — чем платим за низкий порог

Номер лучшего совпадения `find` по всем страницам и запросам (21 замер):

| диапазон | сколько целей |
|---|---|
| 1–50 | 16 (76%) |
| 51–100 | 1 |
| 101–152 | 2 |
| 300–326 | 2 |

Глубокие цели — не выдумка: переключатель темы MDN стоит на 135, результаты поиска
MDN — на 152, дубли подписи «Поиск»/«Войти» на Хабре — на 300 и 326. Порог 50 выводит
их из КАРТЫ, но не делает недостижимыми: нумерация в странице остаётся полной, `find`
ищет по всему снимку. Это утверждение закреплено пином
(`tests/ai/browser-snapshot.test.ts`, «find видит цель ЗА пределами top-N»), и пин
проверен мутацией — при обрезке поиска до карты он краснеет один, остальные 28 зелёные.

Тонкое место названо прямо: иконка поиска Хабра — **номер 46 из 50**. Запас четыре
номера. Эталонный сценарий приёмки от этого не зависит (он идёт через `find`), но
следующий читатель должен видеть, насколько узко.

### Д6 — накопление контекста за прогон

Механика: API-путь пересылает всю историю каждым ходом, поэтому результат первого хода
уезжает провайдеру столько раз, сколько ходов осталось. Замер даёт две цифры вместо
одной, и они отвечают на разные вопросы.

**Живая (с кэшем).** 79–98% входа — попадания в prompt-кэш. Полную цену платит только
свежий кусок хода, то есть сам результат инструмента. Доля снимка в свежих токенах:

| прогон | снимки | read_page | доля снимка в свежих |
|---|---|---|---|
| DeepSeek · каталог | 3 333 | 4 812 | **41%** |
| Gateway · каталог | 3 347 | 4 878 | **46%** |
| Gateway · форма | 2 112 | 0 | 21% |
| DeepSeek · Хабр | 690 | 3 241 | 10% |

**Расчётная (без кэша), из `browser-page-bench`.** Сценарий из 10 действий на полном
наборе инструментов продукта, постоянная часть хода — 18 678 токенов (system 3 041 +
схемы **82 инструментов** 15 637):

| страница | snapshot каждый раз | snapshot top-150 | find первым |
|---|---|---|---|
| М.Видео | 448 998 | 253 447 | **204 130** |
| Хабр | 277 920 | 230 473 | **195 402** |
| GitHub | 250 382 | 232 872 | **191 715** |
| форма | 188 331 | 188 331 | 188 858 |

Эти две цифры **не заменяют друг друга**: расчётная показывает верхнюю границу для
провайдера без кэша, живая — что платится на самом деле у DeepSeek и Gateway. Приёмочная
цифра Д6 (3.7M токенов и $1.04 на одну задачу 10.08) относилась к полному агентному
циклу продукта с 82 инструментами и провальным прогоном на 51 вызов; здесь мерилась
браузерная ось на 5–7 ходов, поэтому цифры несопоставимы напрямую и заменой той не служат.

### Чем модели пользуются на самом деле

Описания инструментов объявляют `find` основным путём, а `snapshot` — запасным. Факт:

- `find` использован в **3 прогонах из 6**, первым ходом — в одном;
- `read_page` — в 5 из 6, первым ходом в 4;
- в обоих тяжёлых прогонах самым дорогим вызовом оказался **`read_page`** (4 812 и
  4 878 токенов), а не снимок;
- на одной и той же форме DeepSeek обошёлся одним `find` (57 токенов), Gateway взял два
  снимка (2 112) — результат одинаковый.

Отсюда практический вывод, стоящий за понижением порога: **порог работает независимо от
того, слушается ли модель инструкции.** Описания можно переписывать сколько угодно —
цену снимка задаёт константа.

## 4. Методика и её границы

- **Страница грузится в `BrowserWindow`, а не в `<webview>` окна приложения.** CSP
  приложения к чужой странице сознательно не применяется (`csp-scope.ts`, 12.08) — здесь
  его просто нет, то есть то же, что в проде после починки.
- **Скрытое окно даёт ~2 кадра в секунду.** Разведка 13.08 показала, что скрытая
  поверхность может выполнить сеть и не отрисоваться вовсе, поэтому у каждого прогона
  меряется rAF. Проведён контрольный прогон видимым окном (`--show`):

  | страница | элементов скрыто / видимо | полный снимок | read_page |
  |---|---|---|---|
  | Хабр | 346 / 346 | 4 974 / 4 974 | 2 856 / 2 854 |
  | М.Видео | 835 / 835 | 14 848 / 14 848 | 4 466 / 4 469 |
  | GitHub | 215 / 215 | 3 540 / 3 540 | 1 276 / 1 276 |

  Числа совпадают — скрытая поверхность мерит то же самое.
- **Выдача Хабра снимается только действием.** Прямой URL с `?q=` отдаёт заглушку (47
  элементов) — штатное поведение Хабра для всех браузеров. Бенчмарк сам проходит путь
  приёмки: `find «поиск»` → клик по ПОСЛЕДНЕМУ совпадению (иконка формы, №46; первое —
  ссылка шапки) → ожидание → замер. После действия 346 элементов и заголовок
  «Результаты поиска по запросу «electron» / Хабр».
- **`browser-run-bench` изолирует браузерную ось:** модели даются только 8 браузерных
  инструментов, нет гейтов режима, подтверждений, компакции и планов. С полным набором
  дешёвая модель уходит в файлы и команды, и замер перестаёт быть о браузере. Поэтому
  первый ход там стоит 5 362–6 574 токена по факту, а не 18 678 расчётных на полном
  наборе, — цифры из разных срезов не смешивать.
- **Оценка токенов — `chars/4`**, та же грубая формула, что у продукта. Сверка с живым
  usage DeepSeek: расхождение есть, но в отчёте везде, где возможно, стоит фактический
  usage провайдера, а расчётные цифры помечены расчётными.

## 5. Находки, которых постановка не заказывала

1. **`loadURL` может не завершиться никогда, и в продукте это не ограничено.**
   `window.verstakBrowser.navigate` (`BrowserView.tsx`) делает `await wv.loadURL(target)`
   без потолка. Поиск Хабра держит открытые соединения, `did-finish-load` не наступает —
   ход агента повисает до отмены человеком. Мой измеритель на этом простоял **1 час 48
   минут** без единой строки вывода, прежде чем я его снял; в продукте это выглядело бы
   как «агент завис». Чинится потолком на вызов (в бенчмарках сделано, в продукте —
   нет: правка браузерного пути выходит за границы куска).
2. **Стоимость завышается на кэшируемых прогонах.** Учёт `inclusive`: `inputTokens` уже
   включает `cacheReadTokens`, но стоимость считается по цене `input` для всей суммы. У
   DeepSeek кэш-попадания тарифицируются дешевле, а их 79–98%. Зона денег, не браузера.
3. **Анти-бот-заслоны.** См. `npmjs.com` выше.
4. **`shared/` не покрыт линтом вовсе.** Замечено при прогоне гейта над собственной
   правкой: `lint:changed` взял один файл из двух, а `eslint shared/browser-snapshot.ts`
   ответил «File ignored because no matching configuration was supplied». В
   `eslint.config.mjs` набор правил объявлен для `electron/**`, `src/**`, `tests/**` —
   каталога `shared/**` в списке нет, хотя его импортируют оба слоя (52 файла в
   `electron/`, 10 в `src/`). То есть «0 errors» в `lint:full` получено в том числе
   потому, что этот каталог не смотрели. `tsc` его проверяет, линт — нет.
5. **Одинаковые подписи — живой, а не теоретический случай.** «Поиск» на Хабре: ссылка
   шапки №5 и иконка формы №46/№326. Предупреждение в `vskFind` работает; бенчмарк
   вынужден брать последнее совпадение, потому что первое — не то.

## 6. Что НЕ сделано

- **Shadow DOM / iframe отдельно не мерились.** Кандидат из PLAN в этот кусок не взят:
  ни одна из семи страниц не упёрлась в бюджет рекурсии (`truncatedByBudget` не
  выставился ни разу), то есть материала для замера на этих страницах нет.
- **Описания инструментов не переписаны.** Живые прогоны показали, что модели их не
  слушаются, но правка описаний меняет поведение продукта и границей куска запрещена —
  выношу решением штабу вместе с цифрами.
- **Правка `navigate` в продукте не делалась** (находка 1) — та же граница.
