## 2. Что такое PerChatState и зачем он был в плане

Идея из AGENTS.md п.5: `map chatId → ChatStateBundle` вместо двух форм хранения
одного и того же — top-level поля активного чата + `chatSnapshots` фоновых.

Боль, которую это должно закрыть:
- Два представления одного состояния обязаны синхронизироваться через
  capture/restore — исторический источник drift-багов (#3, #8, 2.0.1, finding 2/3).
- Каждый event-router обязан различать «активный чат или фоновый»
  (`applyEventToSession` vs `applyEventToChat`) — двойная логика.

**Честная переоценка после срезов 1-3:** capture/restore уже сошлись в чистые
функции (`session-snapshot.ts`) и единые билдеры (`chat-lifecycle.ts`), drift-классы
запинены тестами. Остаточная боль PerChatState = двойная логика event-routing
и ~150 строк snapshot-механики. Это меньше, чем казалось при написании FIX-PLAN.

## 4. Варианты

### Вариант A — «большой взрыв»
Заменить top-level поля на `chats: Record<number, ChatStateBundle>` одним PR.
**Отвергнут**: 45 читателей ломаются разом, ревью невозможно, откат болезненный.
Прямое нарушение AGENTS.md («не делать version 3.0 одной большой PR»).

### Вариант B — strangler в 4 среза (рекомендуемый, если делаем)

**Срез 4.1 — Writers-first (низкий риск, внешний API store не меняется).**
Ввести `updateChatBundle(chatId, updater)` — единую точку мутации bundle по chatId
(активный = top-level, фоновый = snapshot). Все ~10 существующих экшенов
(addMessage, updateLastAssistant, setStreaming, applyEventToSession и т.д.)
перевести на него ВНУТРИ store. Снаружи ничего не меняется.
Приёмка: 116 store-тестов зелёные без правок + новые тесты на updateChatBundle.

**Срез 4.2 — Единое хранилище.**
`chats: Record<number, ChatStateBundle & { hasUnread?: boolean }>` становится SSOT;
top-level bundle-поля активного чата превращаются в поддерживаемую проекцию
(временно, с sync-стражем в тестах: после каждого экшена top-level ≡ chats[activeChatId]).
`chatSnapshots` объявляется deprecated-вьюхой (`chats` минус активный).
Приёмка: sync-страж + весь харнес зелёный.

**Срез 4.3 — Readers (самый дорогой).**
Хук `useActiveChatBundle()` + миграция читателей: Chat.tsx отдельным коммитом,
далее по 2-3 компонента на коммит. Каждый коммит — гейт.
Приёмка: ни один компонент не читает top-level bundle-поля напрямую (lint-правило/греп-страж).

**Срез 4.4 — Удаление дублей.**
Top-level bundle-поля и `chatSnapshots` удаляются; lifecycle-билдеры среза 3
упрощаются (capture/restore → перекладывание в map). Event-router сливается
в один `applyEventToChat(chatId, event)`.
Приёмка: удалено ~200 строк, харнес зелёный.

Оценка: 4–6 сессий. Каждый срез — отдельный откатываемый коммит.

### Вариант C — стоп после 4.1/4.2
Признать, что срезы 1-3 закрыли ~80% практической ценности, и остановиться
на writers-first (4.1) как финальной форме: двойное хранение остаётся, но все
мутации идут через одну точку, drift зажат тестами. Экономия: 3-4 сессии.

## 5. Рекомендация

1. **4.1 делать в любом случае** — дёшево (1 сессия), внешний API не ломается,
   снимает класс «забыли обновить вторую копию» на уровне механики.
2. После 4.1 — **точка решения**: 4.2-4.4 (полный PerChatState) или стоп (вариант C).
   Критерий: если в ближайшие релизы идут фичи, активно трогающие фоновые чаты
   (debate mode, мультиагент fan-out), полный PerChatState окупится; если нет —
   остановиться на варианте C.
3. 4.3 не начинать без свежей оценки: это половина всей стоимости при наименьшей
   добавленной надёжности (читатели не порождают drift, только писатели).

## 6. Риски и страховка
