# Задача 10 — Оркестратор по умолчанию: предложение (последняя, с разбора)

Цель (бриф): любой чат получает задачу → изучает проект → пишет ТЗ → просит открыть
новый чат для исполнения; либо режим авто, где делает сам.

## Что уже построено (не изобретать заново)
- **Автопрогрев Brain** (задача 3, сделано) — «изучает проект» уже происходит фоном при
  открытии/смене проекта. Оркестратору есть на что опереться.
- **Режим `plan`** (один из 5 режимов) — модель уже умеет писать план/ТЗ вместо правок.
- **Dev-task flow** (`dev_tasks`, DevTaskPanel, TaskContractReview) — контракт задачи с приёмкой.
- **Планы** (`plans`/`plan_steps`, вкладка План) — многошаговые планы с шагами/статусами.
- **delegate/orchestrate/swarm** — исполнение силами суб-агентов.
- **Handoff-паттерн** (Open Design #12, разбор задачи 9) — сжать диалог в самодостаточное
  «первое сообщение» для свежего чата. Этого у Verstak пока НЕТ — ключевой недостающий шов.

## Жёсткий урок, который нельзя нарушить (§4.1 CLAUDE.md)
Команда уже пробовала «авто-план на аудите» через директиву в system-layer и через идею
классификатора в main — **обе отвергнуты Павлом**. Причина зафиксирована: main видит
только ПЕРВОЕ сообщение, а модель — всю траекторию; классификатор «простая/сложная» в коде
СТРОГО ХУЖЕ модели. Значит **триггер оркестрации решает МОДЕЛЬ по ходу, а не код по первой
фразе**. Оркестратор-по-умолчанию — это не main-детектор «это большая задача», это
поведение, которое модель применяет сама, а UI лишь ДАЁТ ей инструменты и делает шаги видимыми.

## Предложение: оркестратор = поведение модели + два готовых шва

### Шов 1 — «Изучить и составить ТЗ» (по умолчанию для крупной задачи)
Модель, получив задачу, которую САМА оценила как крупную/изменяющую, идёт по пути:
изучить (Brain уже тёплый) → составить ТЗ (dev-task контракт + план) → показать пользователю.
Это уже достижимо режимом `plan` + create_plan. Доработка — не новый детектор, а:
- Промпт-шов в протоколе: «крупная задача → сначала ТЗ/план, потом исполнение» (мягкая
  директива, НЕ гейт — модель следует или нет; живой пример §4.1 показал, что жёсткую
  директиву модели игнорируют, поэтому это ориентир, а надёжность даёт UI ниже).
- UI: когда модель создала ТЗ/план — карточка с двумя кнопками: **[Исполнить в новом чате]**
  и **[Сделать здесь (авто)]**.

### Шов 2 — Handoff в новый чат (недостающий кусок)
Кнопка **[Исполнить в новом чате]**:
- Синтезирует seed-сообщение (ТЗ + релевантный контекст проекта из Brain) — как
  handoff-design.ts у Open Design.
- Создаёт новый чат (multi-chat уже есть) с этим seed как первым сообщением.
- Зачем новый чат: чистый контекст под исполнение, отделённый от обсуждения. Это и есть
  «просит открыть новый чат» из брифа — но не «просит текстом», а даёт кнопку.

### Режим АВТО
Кнопка **[Сделать здесь (авто)]** (или пер-чат тумблер «авто-оркестратор»):
- Тот же ТЗ/план исполняется сразу силами delegate/orchestrate/swarm, без ручного нового чата.
- Прогресс/статусы — в конвейере прогона («История работы», задача 1).

## Ключевые продуктовые развилки — ЭТО РЕШАЕТ ПАВЕЛ
1. **Дефолт вкл/выкл.** «Оркестратор по умолчанию» — это дефолтное поведение всех чатов
   или пер-чат тумблер? (Рекоменд: пер-чат тумблер + глобальный дефолт в настройках, чтобы
   обычный быстрый вопрос не превращался в ТЗ.)
2. **Порог «крупной задачи»** отдаём МОДЕЛИ (урок §4.1), не коду. Согласны?
3. **Handoff по умолчанию новый чат или авто?** (Рекоменд: показать обе кнопки, дефолт —
   новый чат для крупного изменяющего, авто — для читающего разбора.)

## Что не делаем
- НЕ классификатор «простая/сложная» в main на первой фразе (отвергнуто, §4.1).
- НЕ жёсткий гейт, заставляющий ТЗ на каждый запрос (превратит быстрый вопрос в бюрократию).

Итог: оркестратор-по-умолчанию собирается из УЖЕ построенного (Brain-автопрогрев + plan +
dev-task + план + мультиагент + история-работы-конвейер) плюс ОДИН новый шов — handoff-seed
в новый чат. Триггер — у модели, надёжность и видимость — в UI (карточка ТЗ с двумя кнопками).
Это последняя задача и самая продуктовая — финальную форму и три развилки выше решает Павел,
код — после разбора с ним.
