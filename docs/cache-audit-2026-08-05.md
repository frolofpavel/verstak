## 1. Что уходит провайдеру на каждом ходе

**История пересобирается и отправляется целиком каждый ход** — это устройство
OpenAI-совместимого протокола, не дефект. Вопрос лишь в том, насколько она сжата.

Сжатие построено и **реально вызывается** (проверял: сначала не нашёл вызовов и
чуть не записал в мёртвый код — имя функции отличалось от ожидаемого):

| Механизм | Где вызывается | Что делает |
|---|---|---|
| `compactToolHistory` | `runner-api.ts:710`, каждый ход | результаты тулзов старше 3 ходов → короткий маркер |
| `capFreshResults` | внутри него же | свежие результаты > 12 000 симв. → умное сжатие |
| `microcompactIfNeeded` | `runner-api.ts:1316` | внеплановая подчистка при подходе к лимиту |
| `shouldAutoCompact` → `createCompactedHistory` | `runner-api.ts:1325`, `1370` | вся история → суммаризация |

Ключевые константы: `KEEP_RECENT_TURNS = 3`, `FRESH_RESULT_HARD_CAP = 12 000`,
маркеры старых результатов — короткие строки вида `[compacted: read_file
(48213 симв., turn 4) — обрезано sliding window, перечитай если нужно]`.

**Взаимодействие с кэшем — благоприятное, вопреки первому подозрению.** Я
проверял гипотезу «сжатие переписывает историю каждый ход и тем убивает
автоматический префиксный кэш». Она **не подтвердилась**: сжатие детерминировано и
движется вперёд вместе с ходом — то, что уже стало маркером, маркером и остаётся.
Меняется только хвост (последние ~3 хода), а это ровно та часть, где и так новый
текст. Префикс из маркеров стабилен и кэшируется.

Единственное событие полного сброса кэша — **авто-суммаризация**: история
заменяется пересказом целиком. Она редкая и оправданная, но стоит знать, что
следующий ход после неё идёт по полной цене.

## 2. Кэш-поля и деньги — здесь дефект

### 2.1. Verstak читает кэш-поля, но ОДНО имя на всех

`openai-compat.ts:189-199` читает единственное поле — `prompt_tokens_details.cached_tokens`
(имя из OpenAI), с пометкой `inputAccounting: 'inclusive'`.

Другие провайдеры разобраны честно и каждый по-своему: Claude — `cache_read_input_tokens`
+ `cache_creation_input_tokens`, `'exclusive'` (`claude.ts:174`); Codex —
`input_tokens_details.cached_tokens`, `'inclusive'`; Gemini — свой путь. То есть
механизм в принципе есть и продуман.

**Проблема в том, что все 11 OpenAI-совместимых провайдеров идут через ОДНО имя
поля.** Если провайдер сообщает кэш под другим ключом (у DeepSeek это исторически
`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` верхним уровнем, а не
`prompt_tokens_details`), Verstak его **не увидит** и посчитает `cached = 0`.

Проверить это можно только живым ответом API — см. §4. Но статически видно, что
других имён код не пробует вовсе.

### 2.2. У дешёвых моделей НЕТ цены кэша — и это даёт ошибку в деньгах

Таблица цен (`src/lib/pricing.ts`, дублируется в `electron/ai/cost-guard.ts`)
содержит поле `cached` **только у четырёх моделей Claude**. Ни у одной из 51
остальных — включая `deepseek-v4-flash`, `deepseek-v4-pro`, все `kimi-*`,
`qwen-*`, `mistral-*`, `gpt-*` — цены кэша нет.

Расчёт (`pricing.ts:129-134`):

```
billableInput = billableInputTokens(...)          // при 'inclusive' вычитает cached
inputCost     = billableInput × price.input
cachedCost    = price.cached ? cached × price.cached : 0     // ← без price.cached даёт 0
```

Отсюда **две ошибки противоположного знака**, обе из одного корня:

| Случай | Что происходит | Куда врёт счётчик |
|---|---|---|
| Провайдер отдаёт `prompt_tokens_details.cached_tokens` | `cached` вычтен из input, а `cachedCost = 0` (цены нет) | **ЗАНИЖАЕТ** |
| Провайдер отдаёт кэш под другим именем | `cached = 0`, весь input по полной цене | **ЗАВЫШАЕТ** |

Занижение — опаснее. Контроллер расхода существует ради порогов «жёлтый > $2,
красный > $5»; счётчик, который занижает, срабатывает позже, чем должен.

**Прямая связь с задачей 2.** В сценарии «папка → отчёт → DOCX» расход показывается
итоговой суммой, а модели предписаны ровно дешёвые — DeepSeek и Kimi. Это те самые
строки таблицы, где `cached` отсутствует. Пока поле не заведено, «видимый расход»
в приёмке A1 систематически смещён.

### 2.3. Дубль таблицы цен: НЕ разошёлся по ценам, но разошёлся по составу

CLAUDE.md §5 держит `PRICES` кандидатом на переезд в `shared/`. Замер:

- рендер (`src/lib/pricing.ts`) — **55** записей;
- main (`electron/ai/cost-guard.ts`) — **52** записи;
- **цены совпадают везде**, дрейфа тарифов нет;
- main не хватает трёх: `glm-5.2`, `glm-5-turbo`, `kimi-for-coding` — все `0/0`.

Последствие узкое, но реальное: при **включённом** лимите расхода неизвестная
модель считается по `FALLBACK_PRICE` (`cost-guard.ts:175-182`). То есть на этих
трёх подписочных моделях экран показывает $0, а страж лимита копит деньги и может
упереться в потолок на том, что ничего не стоит. При выключенном лимите — не
считается вовсе, расхождения нет.

Нормализация (`normalizedUsage`, `billableInputTokens`) живёт в
`shared/contracts/usage.ts` и общая для обоих слоёв — дублируется только таблица.

## 3. Вывод и что делать

**Сколько стоит ход в длинном чате.** Точную цифру назвать нельзя без замера (§4),
но структура такова: история отправляется целиком каждый ход, при этом старше трёх
ходов от результатов тулзов остаются только маркеры. То есть рост input'а с длиной
сессии — **линейный по числу ходов**, а не квадратичный по объёму прочитанного,
как было бы без сжатия. Основной вклад в длинном чате даёт не история тулзов, а
system prompt + context pack + свежий хвост.

**Дешёвые улучшения, по убыванию отношения польза/риск:**

1. **Завести `cached` (и где есть — `cacheWrite`) для OpenAI-совместимых моделей**
   в обеих копиях таблицы. Это не оптимизация, это починка счётчика: сейчас он
   врёт в обе стороны. Самое дешёвое и самое полезное.
2. **Читать не одно имя поля, а несколько.** Добавить в `openai-compat.ts`
   разбор альтернативных ключей (`prompt_cache_hit_tokens` и т.п.) с сохранением
   текущего как основного. Иначе кэш у части провайдеров невидим в принципе.
3. **Довести три недостающие записи в `cost-guard.ts`** — или, лучше, перевезти
   `PRICES` в `shared/` следом за `plan_approval_gate`: расходиться станет нечему.
   Дубль уже разошёлся по составу, это не гипотеза, а замер.
4. **Стабильность префикса трогать не нужно** — проверено, сжатие кэшу не мешает.
   Единственный сброс — авто-суммаризация, и он оправдан.

Порядок правок: 1 → 3 → 2. Пункт 2 требует живых ответов API для проверки, пункты
1 и 3 доказываются юнит-тестом.

## 4. Несделанный остаток — живой замер

**Что не сделано:** размер payload по ходам на реальном диалоге 5+ ходов и
фактическое содержимое `usage` от DeepSeek и Kimi.

**Почему:** нет запущенного приложения и ключей. Вывод вместо замера был бы
подделкой — тем самым, за что в этой же работе отклонён «DeepSeek успел
дозавершиться».

**Как досъёмить (десять минут, не заново разбирать):**

1. Открыть Verstak, чат на DeepSeek, провести диалог 5+ ходов с 2-3 вызовами
   `read_file` покрупнее.
2. Снять сырой `usage` каждого ответа — точка `openai-compat.ts:189`, там уже
   лежит распарсенный чанк; временный `console.error` с `JSON.stringify(u)` даст
   фактические имена полей. **Убрать сразу после замера** — сырой дамп ответа мимо
   чистильщика однажды уже уезжал в лог (`f7f7150`).
3. Ответ на главный вопрос: присутствует ли `prompt_tokens_details.cached_tokens`,
   и если нет — под каким именем DeepSeek отдаёт попадание в кэш.
4. Сверить показанную в шапке стоимость с фактической по биллингу провайдера за
   тот же диалог. Расхождение и есть цена дефекта §2.2.
