# Задача 7 — Workflows и Решения: ПЛАН ПОСТРОЙКИ (подход утверждён, код по этому плану)

Штаб утвердил подход целиком: workflow = сохранённый повторяемый прогон (три глагола),
решения = журнал «почему», привязанный к прогону. Здесь — конкретный план кода.

## Почему не сделано этой сессией (честно)
Обе половины требуют МИГРАЦИИ БД (новая таблица user-workflows / поле runId у решений). §3.1:
миграции — только append, никогда edit/reorder; ошибка ловится на реальной БД, не всегда
гейтом. Конец длинной сессии — не время для миграции. Un-`soon` без бэкенда преждевременен:
`soonReason` прямо про «нужен сценарий СОЗДАНИЯ» — а создание и есть недостающий бэкенд.
Поэтому — план для чистой постройки со свежим бюджетом, а не полу-собранная фича.

## ЧАСТЬ A — Workflow = сохранённый повторяемый прогон
Сейчас: `WORKFLOWS` — статичный реестр (built-in), `workflows:start` строит промпт+план.
Нет пользовательских workflow и «сохранить из прогона».

Шаги:
1. **Миграция** (новый индекс в MIGRATIONS): таблица `user_workflows`
   (id, project_path, name, brief_template, steps_json, default_provider, default_model, created_at).
2. **storage/user-workflows.ts**: create / listByProject / get / remove.
3. **IPC `workflows:save-from-run(runId)`**: читает план прогона (plan_steps по planId прогона)
   → сохраняет как user_workflow (name = заголовок прогона, steps = шаги плана). Переиспользует
   существующий Skill-Capture-паттерн (RunDetail уже умеет «В скилл»).
4. **`workflows:list`**: мержит built-in `WORKFLOWS` + user_workflows проекта (флаг источника).
5. **UI**: кнопка «Сохранить как workflow» в RunDetail (рядом с «В скилл»/Proof Pack, задача 1 Обзор).
6. **Снять `soon`** с пункта Workflows (теперь сценарий полон: сохранить→запустить→статусы;
   статусы уже рисует конвейер прогона из задачи 1).
Тесты: save-from-run пишет workflow из шагов плана; list мержит built-in+user; пустой план → честный отказ.

## ЧАСТЬ B — Решения = журнал «почему», привязанный к прогону
Сейчас: `DecisionRecord` (project-brain) без runId; DecisionsPanel показывает плоский список.

Шаги:
1. **Миграция**: добавить `run_id TEXT NULL` в таблицу решений (append-only ALTER или новый столбец).
2. **saveDecisionHandler / NewDecisionRecord**: принять и писать runId (из ctx текущего прогона).
3. **RunDetail (задача 1, вкладка Обзор)**: секция «Решения этого прогона» — decisions с этим runId.
4. **DecisionsPanel**: показать привязку к прогону (ссылка на «Историю работы»), снять `soon`.
5. (Позже, отдельно) «всплывает в контексте» — агент видит прошлое решение, когда собирается иначе.
   Это агент-поведение (промпт-шов + подтяжка релевантных решений в контекст) — своя постановка.
Тесты: решение с runId читается по прогону; getDecisionRecords обратно совместим (runId null у старых).

## Порядок
A (workflows) и B (decisions) независимы — можно параллельно/по одной, каждая свой коммит+гейт.
Каждая миграция — отдельно, с проверкой на реальной БД (открыть/закрыть проект, убедиться, что
старые данные целы). Эталон EXPECTED_TOTAL_TESTS поднять под новые пины.

Оценка: A ~1–1.5 дня, B ~1 день. Обе — обычные вертикали (миграция+storage+IPC+UI+пины), риск
только в аккуратности миграции.
